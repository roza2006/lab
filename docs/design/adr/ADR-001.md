# ADR-001：采用模块化单体与 DDD 分层

| 项目 | 内容 |
|---|---|
| 状态 | 已接受（2026-11-10） |
| 决策者 | 刘飞燕、李梓语、代香晰、郝佳鑫、魏宇佳、班国勇 |
| 关联 | `docs/design/architecture.md`、`docs/design/domain-model.md` |
| 复审时间 | R4 结束（处方审核链路稳定后） |

## 背景

系统要在 8 周内完成问诊、处方、审核、流转、核销五条链路，团队成员 6 人，开发时间分散。处方状态迁移必须保证一致性，不能出现“处方已通过但流转单没生成”这类脏数据。课程环境只有本地机器，不想为了演示再维护注册中心、配置中心和消息队列。

## 备选方案

### A. 传统三层单体

Controller → Service → Mapper，按技术层分包。开发最快，但处方状态很容易散落在多个 Service 里；后面加“撤回”“驳回重提”时，改一处漏一处。

### B. 微服务

按问诊、处方、流转拆服务。边界清晰，但处方审核到流转会变成跨服务调用，需要处理超时、重试、分布式事务和链路追踪。课程周期内，联调成本高于收益。

### C. 模块化单体 + DDD 分层

一个 Spring Boot 进程，按限界上下文分包；每个上下文内部再分 `domain / application / interfaces / infrastructure`。处方、明细、流转、审计仍在本地事务里，边界通过包依赖和评审约束。

## 决策

采用 **C：模块化单体 + DDD 分层**。

具体落地：

- `com.medical.platform.identity`、`consultation`、`prescription`、`circulation`、`catalog`、`audit` 六个上下文；
- `domain` 不依赖 Spring/MyBatis，状态迁移只写在聚合方法里；
- Controller 只做参数校验、权限注解和 DTO 转换；
- 跨上下文调用走应用服务；需要异步的用事务发件箱；
- 未来如果流转或通知真的需要独立扩容，再把对应包拆成服务。

## 后果

### 好的方面

- 处方状态、明细、审计可以在一个本地事务里提交，演示时不会出现半成功；
- 单进程启动，组员本地不需要装一堆中间件；
- 领域层可以脱离数据库做单元测试，状态机测试写起来快；
- 包边界清楚，六个人按上下文分工，减少互相改同一个文件。

### 需要接受的代价

- 没有强制服务边界，靠包结构和代码评审约束；如果图省事跨包直接调 Mapper，边界会慢慢烂掉；
- 单进程部署，某个模块内存泄漏会影响全部功能；
- 后期拆服务时，需要把跨上下文调用改成 HTTP/消息，不能一键完成；
- `domain` 不依赖 Spring 会让一些脚手架代码变多，但换来的是可测试性。

## 后续动作

1. R2 按上下文建包，先落 Identity 和 Prescription 的骨架；
2. R3 登录链路先跑通，补 `@PreAuthorize` 和数据范围校验；
3. R4 处方状态机完成后，用 ADR 复审是否仍不需要拆服务；
4. 如果 R4 发现单进程无法支撑演示并发，再单独评估流转上下文拆分，不提前做。
